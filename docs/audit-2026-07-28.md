## 1. Reported bug: freeze on first cold launch when tapping "Start Recording" — ROOT CAUSE [confirmed by code analysis]

Symptom: first cold launch, complete onboarding, tap **Start Recording** → UI freezes
for seconds (countdown stuck at "5"), then recovers. Not reproducible on later launches.

It is a race between the onboarding camera *pre-warm* and `CaptureScreen`'s own session
bring-up, with the main thread repeatedly blocking on `AVCaptureSession`'s internal lock,
amplified by first-launch disk contention:

1. **Onboarding starts a long camera bring-up and leaves.**
   `CameraPermissionPageView.requestAndPrewarm` (lines 139–149) calls
   `setupSession(.front, 30)` + `resumeSession()` right after permission grant. That
   queues a full `configureSession` (AVAudioSession `.playAndRecord` activation, input/
   output rebuild, 1080p format negotiation) plus `startRunning()` on `sessionQueue` —
   seconds of serial work on a cold start.
2. **First launch only: `ProSwingSeeder` is hammering disk + mediaserverd at exactly
   this moment** (19 clip copies ~59 MB + 19 synchronous `AVAssetImageGenerator` passes,
   kicked off from `App.init`). Camera bring-up stretches from ~1 s to many seconds.
   This is why the bug only reproduces on the *first* cold launch.
3. **The tap blocks the main thread against that in-flight work.** `AVCaptureSession`
   serializes all API access on an internal lock, so while `sessionQueue` is inside
   `configureSession`/`startRunning`, every main-thread touch of the session waits:
   - `CameraPreviewView.makeUIView` → `previewLayer.session = session`
     (`CameraPreviewView.swift:66`) — the classic preview-attach hang;
   - `resumeSession()`'s CAMPERF log reads `captureSession.inputs.count` /
     `outputs.count` **on the calling (main) thread** (`CameraService.swift:365`) —
     the diagnostic added to debug slow starts itself blocks on them;
   - `ensureSessionRunning`'s 100 ms poll of `captureSession.isRunning`
     (`RecordingViewModel.swift:294`) runs on the main actor — one read taken while
     `startRunning` executes parks the main thread until it finishes.
4. **The session is configured twice.** `isSessionConfigured` is written on
   `sessionQueue` at the *end* of configure #1 and read from the main actor with no
   synchronization (`RecordingViewModel.swift:286`) — if the pre-warm hasn't committed
   yet, `CaptureScreen` queues a **second full reconfigure** (stopRunning + remove/re-add
   everything + format renegotiation), roughly doubling the window in which main-thread
   session reads block. Each completed configure also bumps `sessionConfigurationId`,
   whose `.id(...)` keying destroys and recreates the preview view → more main-thread
   `previewLayer.session` assignments racing `startRunning`.

Fix direction (not yet applied): move *all* session access onto `sessionQueue`
(including preview-layer attach, per Apple's AVCam pattern), replace the `isRunning`
poll with a KVO/callback completion signal from `sessionQueue`, drop the
`inputs/outputs` read from the main-thread CAMPERF line, make `configureSession`
idempotent for identical params, and defer `ProSwingSeeder` until the Compare tab is
first opened.

Related, found on the same path:
- **Pre-warm leaves the camera running with nothing showing it** [confirmed]. After
  onboarding, the session keeps running (green privacy indicator) on the ready screen,
  which deliberately renders no preview; nothing stops it until the user opens and
  closes `CaptureScreen` or backgrounds the app. Privacy-signal + battery cost.
- The `CameraService.shared` doc comment ("so the Recording tab can show a live preview
  the moment it mounts") describes the pre-refactor design and is now misleading.

## 2. Defect findings

### Critical

- **C1. Library-cap paywall destroys the recording it interrupts** [confirmed] —
  `CaptureScreen.swift:108` + `RecordingViewModel.cancel()`.
  `.onDisappear(perform: tearDown)` calls `cancel()` with no state guard, and
  presenting the `requiresLibraryUpgrade` full-screen paywall fires `onDisappear`
  (the codebase's own comment on `deactivate()` — `RecordingViewModel.swift:205-207` —
  documents exactly this). Flow: free user with 3 saved swings stops a recording →
  gate blocks save → paywall covers the screen → `onDisappear` → `cancel()` deletes
  the recording file and resets state. Whether they pay or dismiss, the recording and
  its detected swings are gone, and `onAppear` restarts a fresh countdown. The user who
  just paid loses the very clip they paid to save. `deactivate()` has the
  `state == .idle` guard for this exact hazard; `tearDown()` bypasses it.

### High

- **H1. Post-restore self-heal for pro swings can never run** [confirmed] —
  `ProSwingSeeder.swift:34`. `seedIfNeeded` early-returns when `stored >=
  currentSeedVersion && allProsSeeded(...)`, and `allProsSeeded` checks SwiftData
  records only. After an iCloud/device restore the records come back but the media
  files don't (`Videos/Pros` is deliberately excluded from backup) → every pro swing is
  a broken record forever. `seedOne` *does* check record + file and would heal, but the
  early return makes it unreachable.
- **H2. The exportHD premium gate is dead code — every export is ungated** [confirmed] —
  `ExportProgressView.swift:102,153,183`. Two independent kills: (a) the quality picker
  renders only `if layoutConfig == nil`, and the sole live instantiation
  (`ExportFlowCoordinator.swift:65`) always passes a non-nil config; (b) even on the
  legacy path, locked rows are `.disabled(locked)`, so the button action containing
  `featureGateHit` + `showPaywall = true` can never execute. Every export renders at
  the layout's full `exportSize` regardless of subscription; `feature_gate_hit
  {exportHD}` can never fire (matches the zero-data event in Amplitude).
- **H3. Non-trial purchase revenue is double-counted** [confirmed] —
  `CustomPaywallView.swift:210` (`trackConversion`) records `PurchaseRevenue` directly,
  AND `SubscriptionRevenueReporter` (subscribed to the RevenueCat
  `customerInfoStream` in `PurchaseService.observeCustomerInfo`) reports the same
  non-trial transaction from the entitlement update. Currently reachable for
  trial-ineligible users (anyone re-subscribing after a previous trial — intro offers
  are once per Apple ID), i.e. exactly the winback cohort.
- **H4. Comparison composition is built with synchronous, deprecated asset parsing on
  the main thread** [confirmed] — `ComparisonCompositionBuilder.swift:220,236`
  (`asset.tracks(withMediaType:)`), called from `ComparisonViewModel.init` /
  `rebuildComposition` on the main actor. Parses both source movies synchronously on
  the UI thread on every comparison open and every mode/swap change.

### Medium

- **M1. `abortCountdown()` has zero production callers** [confirmed] — the
  changelog's "Spurious 'Camera session is not running.'" fix is unwired
  (only tests call it). Remaining live path: background the app mid-countdown →
  `scenePhase` handler pauses the session, countdown Task resumes on foreground,
  `beginRecording()` hits the paused session → the exact spurious alert again.
- **M2. Recording-finished error branch discards recoverable recordings and leaks the
  file** [confirmed] — `RecordingViewModel.swift:163-172`. AVFoundation routinely
  finishes with an `error` whose
  `AVErrorRecordingSuccessfullyFinishedKey == true` (disk full, max duration,
  interruption) and a fully playable file. The branch never checks it: clip discarded
  from the app flow, file never deleted either.
- **M3. Save failure still reports success** [confirmed] —
  `RecordingViewModel.swift:482-512`. `persistToSwiftData` returns nil on any
  storage/save error; `finalizeSave(with: nil, ...)` still tracks `.swingSaved`, still
  sets `state = .saved`. Clip lands in Photos but silently never appears in History.
- **M4. Whole-file copy on the main actor during save** [confirmed] —
  `RecordingViewModel.swift:486`. `videoStorageService.copyVideoToStorage(from:)` is a
  synchronous call inside a `@MainActor` method — a long recording freezes the UI
  under the saving overlay.
- **M5. Sandbox/TestFlight transactions reported as production revenue** [confirmed] —
  `SubscriptionRevenueReporter.swift:48` never checks `EntitlementInfo.isSandbox`.
- **M6. Revenue dedup is device-local while the entitlement is account-scoped**
  [confirmed] — `SubscriptionRevenueReporter.swift:52`. Reinstall / second device /
  new device re-reports the latest renewal as fresh revenue.
- **M7. `PurchaseService` @Observable state written off the main actor** [confirmed] —
  `PurchaseService.swift:62-70`. `observeCustomerInfo()` runs on the global executor
  (non-isolated class, unstructured `Task`), writing `customerInfo` / `isPremium`
  while SwiftUI reads them on main — the same unsynchronized-@Observable race class
  this branch fixed in `CameraService`. Same for `restorePurchases`/`refreshStatus`.
- **M8. Comparison build failure is invisible to the user** [confirmed] —
  `ComparisonViewModel.swift:92`. `rebuildComposition` guard just logs; the screen
  shows a black video area with dead controls (reachable via `validLocalURL == nil`,
  e.g. after H1 or a failed path migration).
- **M9. `SingleVideoPlayerView` teardown/rebuild asymmetry** [plausible — needs
  device] — `SingleVideoPlayerView.swift:33`. `.onDisappear { viewModel?.cleanup() }`
  paired with sheet presentations; if sheet presentation fires `onDisappear` here (as
  the 07-26 audit observed for `ComparisonView`), playback state resets under the user.

### Low

- **L1.** `DetectionOrchestrator.stop()` (line 105) parks the main thread behind one
  in-flight Vision pass (`processingQueue.sync`); worst case one ~100–300 ms hitch per
  stop under thermal throttle. [confirmed; bounded by the backpressure gate]
- **L2.** `RecordingCoordinator.onMaximumDurationReached` is never assigned — the
  30-minute cap does nothing; recording runs until disk-full, which then lands in M2's
  broken error branch. [confirmed]
- **L3.** `VideoPathMigrationService` sets the completion flag even when `save()`
  throws — deliberate anti-loop tradeoff, but it forfeits the migration forever after
  one transient failure; a capped retry (N attempts) would keep both properties. [confirmed]
- **L4.** Paywall close button lacks an `isWorking` guard — dismiss during an
  in-flight purchase yields `paywall_dismissed` → `paywall_purchased` for the same
  transaction and a double `onDismiss()`. [confirmed]
- **L5.** Pro-swing comparison gate (`HomeView.swift:159`) and the 3-swing library
  gate (`RecordingViewModel.swift:414`) show paywalls without tracking
  `featureGateHit` — per-gate attribution in the funnel undercounts exactly the two
  gates free users hit most. [confirmed]
- **L6.** `SwingReplayView` error strings hardcoded English (`"Video file not
  found"`, `"Video not ready yet"`), bypassing the 13-language catalog. [confirmed by finder]
- **L7.** All `PaywallViewModel` error/status strings + restore toast hardcoded
  English on the conversion-critical screen. [confirmed by finder]

### Design notes (Sandi Metz review of the uncommitted diff)

1. `RecordingViewModel` grew to 554 lines by absorbing four separable concerns
   (camera-callback ownership, abandoned-recording discard, finalize watchdog,
   skeleton subscription) — extract `RecordingSessionOwner` / discard owner.
2. `configureSession()` now interleaves configuration, phase-timing instrumentation,
   and analytics in one 62-line body — extract a `PhaseTimer`.
3. `CameraService` gained pose-overlay geometry derivation (4 stored props + a lock) —
   belongs in a small builder, not the session manager.
4. The `urlPendingDiscard` identity rule is enforced in three places by comments, not
   by a type — extract an `AbandonedRecording` value with `isMine(_:)`.
5. `SwingEditorSheet` embeds AVAssetImageGenerator lifecycle + cancellation policy in
   a View — extract a `FramePreviewGenerator`.

## 3. Test suite

`xcodebuild test` (iPhone 17 sim): 77 passed / 2 failed / 7 skipped.

Both failures exercise code **not modified on this branch** (likely pre-existing):

- `SwingClassifierTests` "Model loads from bundle": `SwingClassifier.init` loads the
  model in a detached Task; the test checks `isAvailable` synchronously right after
  init — an inherent race, red whenever the load loses. The API offers no way to await
  load completion; fix the API (e.g. `func awaitModel()` or injectable loader), not
  the assertion.
- `ValidationScorecardTests` recall 0.80 < 0.95: heuristics-only path
  (no classifier involved), deterministic golden snapshots — the 0.95 bar itself
  appears miscalibrated vs current `PoseHeuristics`. Needs its own investigation;
  nothing in this branch touches the inputs.
