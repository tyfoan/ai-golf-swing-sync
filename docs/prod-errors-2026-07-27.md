## Findings

### 1. Recording pipeline still loses ~89% of attempts (high)

`recording_started` 28 → `swing_saved` 3 in 30 days. Matches the 90-day funnel exactly and is what
the finalize freeze produced: users record, a swing is detected, and the save never completes.

The fix is on branch `fix/recording-freeze-and-audit-2026-07-26` and is **not released**, so this
number should not be expected to move until it ships. Once it does, `recording_stopped` and
`recording_finalize_timeout` become the direct measurement — a `recording_started` without a
matching `recording_stopped` is the freeze's fingerprint.

### 2. No production error visibility on the shipped build (high)

The build users are running has no crash reporting, no hang reporting, and no failure-side events.
Nothing in this report can tell you whether the live version is crashing. The only source that
could is Xcode Organizer.

### 3. Export has never been exercised (medium)

`export_started` / `export_failed` have never fired. Either nobody reaches export — plausible,
given only 3 saved swings — or the entry point is unreachable. Not distinguishable from telemetry
alone until users get that far.

## Manual step — the actual answer for crashes today

> **Xcode → Window → Organizer → Crashes.** Symbolicated, aggregated, from real users, in real
> time, free. There is no API and no CLI for this. It is the fastest and best source for crashes
> on the currently shipped build, and no part of this report replaces it.

Filter to the 1.3.2 release and check for hangs as well as crashes — the app's real failure mode
was an unresponsive main thread, which never appears as a crash.
