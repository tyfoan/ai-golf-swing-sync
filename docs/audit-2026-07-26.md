## 1. The freeze — root cause found and proven

### 1.1 Throwaway `RecordingViewModel` nils the shared camera callbacks (CRITICAL)

`RecordingView.swift:18`

```swift
@State private var viewModel = RecordingViewModel()
```

SwiftUI evaluates a `@State` default-value expression on **every** construction of the enclosing
view struct, keeping only the first instance and discarding the rest. `MainTabView` re-constructs
all four tab children whenever `router.selectedTab` changes.

Each discarded instance runs the full lifecycle against a **shared singleton**
(`let cameraService = CameraService.shared`):

- `init()` → `setupCallbacks()` assigns `cameraService.onRecordingFinished` (RecordingViewModel.swift:102)
- `deinit` sets `onRecordingFinished`, `onFrameCaptured`, `onAudioCaptured` to **nil** (:95–98)

**Empirical proof** (temporary init/deinit logging, iPhone 17 simulator, probe reverted after):
one visit to the Camera tab plus a single History→Camera switch produced

```
3 × PROBE-INIT
1 × PROBE-DEINIT      ← fired last
```

so `CameraService.shared.onRecordingFinished` was **nil while a live `RecordingView` existed**.

**Why that is a hard freeze.** `stopRecording()` (:225–235) sets `state = .finalizingVideo` and
calls `cameraService.stopRecording()`. The **only** exit from `.finalizingVideo` is the
`onRecordingFinished` callback — `CameraService.swift:413`:

```swift
self?.onRecordingFinished?(outputFileURL, error)
```

With the callback nil, nothing fires. There is no timeout and no fallback, so the
`FinalizingVideoOverlay` stays up **forever**; force-quit is the only escape.

Asymmetry that makes this survive: `onFrameCaptured` is re-assigned in `beginRecording()` (:216)
so it self-heals, but `onRecordingFinished` is assigned **only** in `init` — once a throwaway's
`deinit` clears it, it is nil for the rest of the process lifetime.

**Corroborating production data** (Amplitude, 90 days, per-user funnel):
`recording_started` 28 → `swing_detected` 15 → `swing_saved` **3**. Swings are detected, then the
save/finalize step is where users are lost.

**Repro on device:** launch → switch to any other tab → back to Camera → record → Stop.

**Fix (pick one, plus the watchdog):**
1. Don't touch singleton state from `init`/`deinit`. Move wiring to `.onAppear`/`.task` and
   teardown to `.onDisappear`.
2. Construct lazily: `@State private var viewModel: RecordingViewModel?`, built in `.onAppear`.
3. Give `CameraService` token-based/multicast subscriptions instead of single-assignment closures,
   so a stale owner cannot clear a live owner's callback.
4. **Regardless:** add a watchdog timeout on `.finalizingVideo` that surfaces an error and returns
   to `.idle`. A single-point-of-failure callback with no timeout should not gate a terminal UI state.

### 1.2 Main thread blocks on `sessionQueue.sync` during camera setup (HIGH)

`CameraService.swift:190`

```swift
func makePreviewRotationSubject(for layer: AVCaptureVideoPreviewLayer) -> CaptureRotationSubject? {
    sessionQueue.sync { ... }
}
```

Called from `RecordingView.swift:93` inside `CameraPreviewView`'s `rotationSubjectProvider`, i.e.
from `makeUIView`/`updateUIView` on the **main thread**.

The same `sessionQueue` runs `configureSession`, which performs `captureSession.stopRunning()`,
`configurator.configure(...)` (add inputs/outputs), and `configureAudioSession()`
(`AVAudioSession.setActive(true)`). These routinely take hundreds of milliseconds on device, and
`setActive(true)` can take longer when another app holds the audio session.

So entering the Camera tab dispatches `setupSession` async onto `sessionQueue` and then blocks the
main thread on `sessionQueue.sync` for the whole configuration. No hard deadlock (nothing on
`sessionQueue` calls `DispatchQueue.main.sync` — verified: the only two `.sync` sites in the app
are this one and `DetectionOrchestrator.stop()`), but a visible stall.

Made worse by `RecordingView.swift:96`:

```swift
.id("main-camera-\(viewModel.cameraService.sessionConfigurationId)")
```

`configureSession` increments `sessionConfigurationId` at its end, which forces SwiftUI to
**recreate** the preview view, which calls the provider again → another main-thread `sync`. Camera
switching goes through the same path.

**Fix:** make rotation-subject creation async (return nil immediately, deliver the subject via a
callback/`@Observable` property once `sessionQueue` is free) instead of blocking main.

### 1.3 `DetectionOrchestrator.stop()` is NOT a deadlock (checked, clean)

`stop()` uses `processingQueue.sync`. I traced every caller: all four are in `RecordingViewModel`
(:108, :230, :396, :411) on the main actor, and `onSwingDetected` is delivered via
`DispatchQueue.main.async` (DetectionOrchestrator.swift:176) — so `stop()` can never be reached
*from* `processingQueue`. No self-deadlock.

Worst case is main blocking for one in-flight Vision pass; the early-bail guard (:135–138) drops
queued frames. Acceptable.

All five Mar-2026 hardening fixes are still present and intact (`processingQueue.sync` drain,
25 s background-task timer, `replaceCurrentItem(with: nil)`, `isConfiguring` guard, tightened
`PoseHeuristics` thresholds — `minimumDescentFrames` is now 3, up from 2).

### 1.4 The comparison screen dies permanently after any sheet or paywall (HIGH — same root cause)

`ComparisonView.swift:35` tears the player down on disappear:

```swift
.onDisappear { viewModel?.cleanup() }
```

`ComparisonViewModel.cleanup()` (:84–89) does `player.replaceCurrentItem(with: nil)` and removes the
time observer — but does **not** nil the view model. And `onViewAppear()` (:192–201) is guarded:

```swift
func onViewAppear() {
    guard viewModel == nil else { return }   // ← never rebuilds
```

So after any disappear/reappear cycle the player has a nil item and is never rebuilt: the
comparison screen comes back **black and frozen, with no recovery**.

Reachable without leaving the screen, because both of these fire `onDisappear` on the presenter:

- `.fullScreenCover` paywall (:41) — tap a premium mode → paywall → dismiss → black
- `.sheet` export flow (:39) — open the export editor → come back → black

Identical structural mistake to §1.1: teardown wired to a lifecycle callback with no matching
rebuild. Side effect: `comparison_opened` only fires when `viewModel == nil`, so re-entries are
never tracked — part of why that count is 2.

**Fix:** set `viewModel = nil` in `cleanup()`'s call site (so `onViewAppear` rebuilds), or drop the
`onDisappear` teardown and only pause, relying on deinit.

### 1.5 The App Store review prompt can never fire (MEDIUM — costs you ratings)

`ReviewPromptService.shared.recordSwingDetected()` has exactly one caller:
`RecordingSaveService.swift:51`. And `RecordingSaveService` is **dead code** — grepped across the
whole app and test target, nothing references it. `RecordingViewModel` saves via
`PhotosSaveService` + `VideoStorageService` instead.

So the review prompt has never been shown to a single user. For a shipped consumer app, ratings
drive discovery; this is cheap to fix.

**Fix:** call `ReviewPromptService.shared.recordSwingDetected()` from
`RecordingViewModel.finalizeSave(...)`, and delete `RecordingSaveService`.

## 2. Launch path

`golf_sync_swingApp.init()` runs five services synchronously before first paint:

```swift
Analytics.shared.configure()
PurchaseService.shared.configure()
VideoPathMigrationService.migrateIfNeeded(modelContainer: sharedModelContainer)
VideoExportService.cleanupOrphanedExports()
ProSwingSeeder.seedIfNeeded(container: sharedModelContainer)
```

### 2.1 Pro-swing seeding on the launch path (MEDIUM — measured, not the freeze)

On first launch, or any launch where `proSwingSeedVersion < 5`, `ProSwingSeeder` copies 19 bundled
clips into `Documents/Videos/Pros` and generates a thumbnail for each with a **synchronous**
`AVAssetImageGenerator.copyCGImage`.

I benchmarked the exact work on this Mac: **copy 4 ms + thumbnails 347 ms = 0.35 s**. Copies are
nearly free because APFS clones; the cost is the thumbnails. On device expect roughly 1 s.

Real, worth moving off the launch path — but honestly **not** the multi-second freeze you
remember. §1.1 is that.

Note `currentSeedVersion = 5`, so existing users have already been put through a full re-seed five
times. The catalog and bundle match exactly (19/19 verified), and `HistoryView` filters pros out
(`allVideos.filter { !$0.isPro }`), so there is **no** permanent re-seed loop.

### 2.2 60 MB of pro videos duplicated into iCloud-backed storage (MEDIUM)

Verified on the simulator: `Documents/Videos/Pros/` holds 19 files, **61 MB** — while the same
59 MB still sits in the app bundle. So the app permanently occupies ~120 MB for one set of videos,
and `Documents/` is **backed up to iCloud by default**, consuming the user's iCloud quota with
content that ships in the binary.

**Fix:** play the pro clips directly from their `Bundle.main` URLs (no copy at all), or at minimum
seed into `Caches`/apply `isExcludedFromBackup`. This also removes §2.1 entirely.

### 2.3 Checked and clean

- `ModelContainer` uses `try?` with an in-memory fallback — launch cannot hang on store failure.
  The CoreData `Failed to stat path .../default.store` messages on first launch are benign
  (store not yet created); no data-error alert appeared.
- No `.task` at launch in `MainTabView` beyond an analytics call — `DevVideoPreloader` is gone.
- `SwingThumbnailView.loadThumbnail()` correctly uses `Task.detached(priority: .utility)`, so list
  thumbnails are **not** generated on main.

## 5. The positioning problem: your headline promise is 100 % paywalled

`HomeView.swift:159`:

```swift
if (v1.isPro || v2.isPro) && !FeatureAccess.isPremiumUser {
    showPaywall = true
    return
}
```

Onboarding page 1 and the paywall both lead with **"Your swing vs a pro's. Auto-synced."** That
exact action is gated. A free user's only legal comparison is two of their **own** swings — which
requires successfully recording twice, i.e. surviving §1.1.

So the sequence for a new user is: get promised swing-vs-pro → hit a paywall before seeing
anything work → start a trial → still can't get there → cancel. That is precisely the 5/5 trial
cancellation rate.

**The single highest-value change in this document:** let every free user compare their first
swing against a pro at least once — even watermarked, even one-time. Sell the *second* comparison,
HD export, and no-watermark. Value first, then the ask.

Secondary: your own `CLAUDE.md` monetization guidance says "two options max"; the paywall shows
three (Lifetime $79.99 / Annual $49.99 with 1-week trial / Weekly $4.99 with 3-day trial). The
"SAVE 81 %" maths is correct.

### 7.1 The frame-rate gap is the biggest functional difference

Every call site hardcodes `setupSession(position: .front, frameRate: 30)`
(`RecordingViewModel.swift:216`, `RecordingView.swift:185`, `CameraPermissionPageView.swift:143`)
— even though `CaptureSessionConfigurator` already negotiates the best format for a target FPS and
its own default is 60.

At 30 fps a driver swing passes through impact in roughly 4–6 frames. At 120 fps it's 16–24. For an
app whose entire pitch is *frame-by-frame alignment at impact*, 30 fps on the **front** (selfie)
camera is the weakest possible configuration, and the competitor leads with 120 FPS.

**Important caveat — do not just change the number.** `PoseHeuristics` works on per-frame deltas
(`velocityThreshold: 0.5`, `minimumDescentFrames: 3`) tuned for 30 fps. At 120 fps the per-frame
wrist displacement is ~4× smaller, so the velocity gate would never trip and **swing detection
would silently stop working**. The correct change is to decouple the two rates: record at 120 fps
for playback/export, but feed the detection pipeline a ~30 fps subsample (skip frames in
`DetectionOrchestrator.processFrame`, or normalise velocity by frame interval). I deliberately did
not change this as part of this pass — it needs its own change plus a device test.

Also worth reconsidering: `.front` is presumably chosen so the user can see themselves while
setting up, but for golf the phone goes on a tripod and the rear camera is both higher quality and
the only one with high-frame-rate slow-mo modes.

### 7.2 Pricing: weekly is the outlier

Annual and Lifetime match them to the cent. The difference is the entry plan: their **$7.99/month**
vs your **$4.99/week** (≈ $259/yr). For a golfer who practises a few times a month, weekly billing
reads as predatory and makes the annual "SAVE 81 %" framing look like it's rescuing you from a bad
deal you invented. A monthly tier at $7.99–9.99 is the conventional, less hostile ladder — and with
5/5 trials cancelled (§4.3) the current ladder has no evidence behind it.

### 7.3 Where you can win

1. **They're 15 months stale and have 14 ratings.** This niche is small and genuinely winnable.
   Fixing §1.5 so the review prompt actually fires is the cheapest ASO lever you have.
2. **Impact-frame auto-alignment is a real differentiator** — their copy says "line up your swing
   with top golfers" but I found no claim of frame-accurate impact sync (**UNVERIFIED** whether
   theirs is frame-accurate). Lead with it, and *show* it working before asking for money (§5).
3. **"Pro comparisons updated monthly"** is a retention mechanic you don't have. 19 static clips
   give a user no reason to reopen the app. A few new pros per month, delivered remotely, is worth
   more than another comparison mode.

### Live skeleton + PiP on the capture screen (added after the audit)

Four components already existed in the codebase and were wired into **nothing**:
`SkeletonOverlayView`, `SkeletonToggleButton`, `RecordingPiPView`, and `DetectionBorderView`
(whose own doc comment reads "traces around PiP when a swing is detected"). That is why the
capture screen looked plain — the parts were built and never connected.

What was missing was the pipe: `DetectionOrchestrator` never published pose to the UI.

- `DetectionOrchestrator.onPoseDetected` publishes each analysed frame's skeleton on the main
  queue. **Emitted immediately after `poseDetector.processFrame`, above the cooldown and
  window guards** — below them the overlay would have frozen for the full 4 s cooldown after
  every detected swing and not appeared until 15 frames in.
- `RecordingViewModel.isSkeletonEnabled` wires/clears that callback, so while the overlay is
  hidden there is no per-frame main-queue traffic at all. Defaults on.
- `PoseOverlayGeometry` (new, pure value type) owns the whole coordinate mapping: Vision's
  bottom-left Y-up origin → Canvas top-left Y-down, the `.resizeAspectFill` centre-crop, and
  mirroring. **7 unit tests** pin it (centre-maps-to-centre invariant, always-covers, aspect
  preserved, reflection about centre, NaN-safety).
- Mirroring and aspect ratio come from `CameraService.poseOverlayGeometry`, which reads
  `connection.isVideoMirrored` and applies the **post-rotation** buffer ratio. Inferring
  mirroring from `.front`/`.back` looks right on a symmetric pose and is flipped mid-swing;
  using the raw sensor ratio yields a stretched, offset skeleton.
- `RecordingPiPView` now takes `isSwingDetected` and overlays `DetectionBorderView`, so the
  PiP border traces green when a swing is locked in. It stays on the **live camera**
  deliberately: pointing an `AVURLAsset` at the still-being-written recording makes iOS
  terminate the capture, per the existing comments.
- Fixed a latent bug in `RecordingPiPView`: the `.frame(120×160)` was on `content`, but the
  ZStack also holds an infinitely-flexible `Color.clear`, so the tile expanded to fill the
  whole screen. Never noticed because the view had never been rendered.

**Verified on simulator:** toggle renders top-right clear of the top bar and switches
green↔grey; PiP renders at the correct size with badge and border (checked by temporarily
forcing it visible, then reverted).

**NOT verified — device only:** skeleton alignment. I re-tested whether Vision pose works on
the simulator rather than trusting the old note: a real frame decoded from a bundled pro clip
returned **zero joints**. So pose is still unavailable there, and the whole mapping is
unverified against a real body. That is exactly why it is isolated in one pure function — if
the skeleton sits off the golfer on device, `PoseOverlayGeometry.point(for:in:)` is the only
place to correct.

Worth a look when you see it on device: `showDetectionFlash` also drives a full-screen green
wash (`RecordingView`), so a detected swing now produces two green cues at once. If that reads
as noisy, deleting the wash is a 5-line removal.

### Production error tracking (added after the audit)

**Read this first:** the failure that was actually hurting this app was a **hang**, not a crash.
No crash reporter — Sentry, Crashlytics, anything — would have caught the finalize freeze: the
process never died, it just stopped responding. So crash tracking alone would have left you
exactly as blind as before. The two things that would have surfaced it are MetricKit's
`MXHangDiagnostic` and the `recording_finalize_timeout` watchdog event, and both are now wired.

**You already have symbolicated crash reports today, for free.** The app is live, so

Added, with no new dependency:

- `CrashDiagnosticsReporter` — a `MXMetricManagerSubscriber` that forwards MetricKit

single pair would have exposed the freeze months ago.

**Deliberately not sent:** call-stack trees. `callStackTree.jsonRepresentation()` is far too

**Verified:** `app_launched` and `camera_config_failed` fired from a simulator launch and are
**ingested and queryable in Amplitude** (confirmed via the API). The MetricKit XPC connection

**Not verifiable here — and important to understand:** MetricKit payloads are **not real-time**.
iOS delivers them at most once per ~24 h, on a *later* launch, only from real devices, and only

events on the simulator and none the same day even on device. `recording_stopped` and
`recording_finalize_timeout` need a real camera, so they are unverified too.

**If you want real-time crashes with stack traces**, add Sentry — it also has its own app-hang

### Second fix batch — the §1.6 defects (2026-07-27)

The confirmed-but-unfixed items from §1.6, now done:

**1. Data race on the capture callbacks — worse than first reported.** `onFrameCaptured` /
`onAudioCaptured` / `onRecordingFinished` were plain stored properties on an `@Observable` class,
read on `videoOutputQueue`/`audioOutputQueue` at 30–60 fps and written from the main actor. That
is *two* problems: an unsynchronised cross-thread read/write of a closure, **and**
`ObservationRegistrar` access bookkeeping driven from a background thread at frame rate. Now
`@ObservationIgnored` and guarded by `callbackLock`, with copy-out getters so the closure is
invoked *outside* the lock (holding it across the call would serialise the capture path against
writers and invite re-entrancy). Nothing in SwiftUI ever observed plumbing closures.

**2. Black preview after a fast tab switch.** `RecordingView` gated resume on
`cameraService.isSessionRunning` — the `@Observable` mirror written via
`DispatchQueue.main.async`, which lags the real session. Switch tabs quickly and the mirror still
read `true` after `pauseSession()` had stopped the session, so resume was skipped and the preview
stayed black with no further lifecycle event to recover it. Both gates now read
`captureSession.isRunning`, which `beginRecording()` already treated as the source of truth for
exactly this reason.

**3. Lost `mediaServicesWereReset` recovery.** The guard read the `@Observable`
`isSessionRunning` on `sessionQueue` — off-main and possibly stale, silently dropping the
recovery and leaving the camera dead after a media-services reset. Now read on the main actor
(where the question "were we *meant* to be running?" is answerable) before hopping to
`sessionQueue`.

**4. Temp `.mov` leaked on every cancel-during-recording.** `AVCaptureMovieFileOutput` keeps
writing after `stopRecording()` returns, but `cancel()` cleared `recordingURL` immediately, so
nothing ever deleted the file. Now `cancel()` splits the two cases: genuinely recording → hand the
file to a deferred discard consumed by the delegate (deleting inline would race the writer); not
recording → delete immediately, because no delegate callback will ever arrive.

**5. `countdownTask` not cancelled on disappear** (from the first batch) — leaving the tab
mid-countdown let it complete and call `beginRecording()` against a just-paused session.

Two bugs I introduced and caught before shipping, worth recording because both were in *my* fix
rather than the original code:

- The deferred-discard flag could go stale (if `stopRecording()` is a no-op, no delegate callback
  consumes it) and would then throw away the **next** legitimate recording. Fixed by matching on
  **URL identity** rather than on the flag merely being set, which makes the failure impossible by
  construction instead of relying on flag hygiene.
- My first test for it asserted the wrong thing — it passed for the wrong reason, because a
  recording with no detected swings is *intentionally* discarded. The test now asserts the state
  transition, which is what actually distinguishes the discard path (returns early, leaves `state`
  untouched) from normal handling.
