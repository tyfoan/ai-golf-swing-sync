# Bug Audit — 2026-04-25

Audit of golf-sync-swing across detection/camera concurrency, AVFoundation lifecycle, closure/observer/deinit chains, and logic/data integrity. 16 verified defects; ranked by severity.

---

## Tier 1 — Confirmed defects, fix soon

### 1. SwingStateMachine.swift:69-87 — Cooldown auto-expiry is unreachable (multi-swing detection broken)
**This is the only finding that breaks a user-facing feature on every session.**

`DetectionOrchestrator.handleFrame` L109 `guard !stateMachine.isInCooldown else { return }` ensures `stateMachine.handle(event:)` is **never** called while in cooldown. Therefore the `case .cooldown:` branch with `elapsed >= cooldownDuration` (L76-82) is dead code at runtime. Cooldown is exited only via `reset()` from `start()`.

**Evidence multi-swing IS the intent:**
- `RecordingViewModel.detectedSwings: [SwingClip]` — array, not single
- `RecordingViewModel.saveToPhotos` iterates: `for swing in detectedSwings { try await photosSaveService.saveClip(...) }`
- `showSwing(at index:)`, `toggleFavorite(at index:)` are per-index APIs
- `SwingStateMachineTests.cooldownExpires` (L40-49) directly tests cooldown auto-expiry — **the test passes** because it calls `machine.handle(event:)` directly, bypassing the orchestrator gate that makes the branch unreachable in production

So: the unit test gives a green light to a code path that's unreachable from the camera pipeline. **In production, only the first swing of each recording session is detected.**

**Fix:** Either remove the orchestrator-level `guard !isInCooldown` and let the state machine self-expire (matches the existing test), OR keep the gate and have the orchestrator query `isCooldownExpired(at: timestamp)` to call `reset()` once enough time elapses. Add an integration test that runs the orchestrator with two simulated swings.

### 2. PhotosSaveService.swift:51-68 — `defer` registered AFTER throw point (temp file leak)
```swift
let outputURL = FileManager.default.temporaryDirectory...        // L51-53
guard let exporter = AVAssetExportSession(asset: composition...) // L55
await exporter.export()                                          // L62
guard exporter.status == .completed else {                       // L64
    throw PhotosSaveError.exportFailed(...)                       // L65 — throws BEFORE defer
}
defer { try? FileManager.default.removeItem(at: outputURL) }     // L68 — never registered when L65 throws
```
**Why it misbehaves:** if export fails, the throw at L65 happens before the `defer` is registered, so the partial file in `tmp/` is never cleaned up.
**Fix:** Move the `defer { try? FileManager.default.removeItem(at: outputURL) }` to immediately after L53 (where outputURL is created).
**Same family as past fix `1a60de5`.**

### 3. VideoExportService.swift:185-225 — Export temp file leaks on failure
Output URL created at L185-186; if export fails (L222-225) the file persists. Mitigated only by `cleanupOrphanedExports` on next app launch, which can mean GBs of accumulated failed exports between launches.
**Fix:** Add `defer { try? FileManager.default.removeItem(at: outputURL) }` after L186; remove only on success path or wrap success in `let saved = try ...; defer { if !saved { ... } }`.

### 4. DetectionOrchestrator.swift:67-72 — `start()` mutates `baseTimestamp` outside the lock
```swift
func start() {
    isActiveLock.lock()
    isActive = true
    isActiveLock.unlock()
    baseTimestamp = nil          // <-- not under lock
    poseDetector.clearBuffer()
    stateMachine.reset()
}
```
**Why it misbehaves:** `processFrame` reads `baseTimestamp` at L97 on `videoOutputQueue` (capture delegate queue). A frame already in flight when `start()` is called can read a non-nil baseTimestamp, then have it nilled mid-call, then the use at L98 (`timestamp - (baseTimestamp ?? 0)`) becomes inconsistent with what was checked at L97.
**Fix:** Move `baseTimestamp = nil` inside the `isActiveLock` critical section; access `baseTimestamp` under the same lock in `processFrame`.

### 5. CameraService.swift:154-162 — `onAudioCaptured` callback not nilled in `stopSession()`
```swift
func stopSession() {
    onFrameCaptured = nil          // ← only frame is cleared
    sessionQueue.async { [weak self] in
        ...
    }
}
```
The audio sample-buffer delegate continues to invoke `onAudioCaptured?(sampleBuffer)` (L311) for in-flight buffers until the session actually stops. Same pattern as past fix `7e7e72f`.
**Fix:** Add `onAudioCaptured = nil` (and consider `onSessionInterrupted`/`onSessionResumed` too) BEFORE `sessionQueue.async`.

### 6. RecordingCoordinator.swift — No `deinit`; timers can outlive the coordinator
`durationTimer` (L28) and `backgroundTimer` (L31) are scheduled on the main run loop, which retains them until invalidated. If the coordinator is deallocated mid-recording (error path, parent VM tears down), neither `stopRecording` nor `markRecordingFinished` runs, and the timers fire every 0.1s indefinitely with `[weak self]` no-ops.
**Fix:**
```swift
deinit {
    stopDurationTimer()
    endBackgroundTask()
}
```

## Tier 2 — Real defects, lower blast radius

### 7. ComparisonViewModel.swift:71 — `syncOffset` silently 0 if either contact time is missing
**Reproduces together with #14 (NaN seek):** imported video without auto-detection → contactTime = 0 → syncOffset is junk → user scrubs → clamp/seek math goes sideways.
```swift
self.syncOffset = swing1.contactTime - swing2.contactTime
```
If either video imported without auto-detection (contactTime = 0), syncOffset becomes 0 or a large nonsense value, and synced playback is silently misaligned. Tap-to-swap (L188-200) further negates this without validating.
**Fix:** Guard at init: if `swing1.contactTime <= 0 || swing2.contactTime <= 0`, fall back to `.sideBySide` mode and log.

### 8. SwingEditorSheet.swift:20, 187, 197 — `@State private var player: AVPlayer?` never released
`onDisappear { player?.pause() }` at L187 only pauses; doesn't release the AVPlayerItem. Each presentation of the sheet creates a new `AVPlayer(url:)` (L197); the previous player + item leak until the View struct itself is reclaimed.
**Fix:**
```swift
.onDisappear {
    player?.pause()
    player?.replaceCurrentItem(with: nil)
    player = nil
}
```

### 9. VideoPlayerViewModel.swift:38-52 — `cleanup()` not guaranteed; `deinit` only removes time observer
`deinit` removes the time observer but does NOT call `replaceCurrentItem(with: nil)` or `cancellables.removeAll()`. The `.AVPlayerItemDidPlayToEndTime` Combine subscription (L66) holds a strong reference to the publisher chain. If a consuming view doesn't explicitly call `cleanup()`, player + item + subscription leak.
**Fix:** Have every consumer call `.cleanup()` on disappear, OR move all cleanup into deinit (with care: deinit isn't `@MainActor`-isolated so `replaceCurrentItem` calls need to dispatch to main).

### 10. VideoPlayerViewModel.swift:66 — Notification observer bound to `player.currentItem` at init
```swift
NotificationCenter.default.publisher(for: .AVPlayerItemDidPlayToEndTime, object: player.currentItem)
```
Bound to the item at construction. After `replaceCurrentItem` (in cleanup or anywhere else), the publisher is observing a now-detached item; if a new item is set, end-of-playback never fires.
**Fix:** Subscribe with `object: nil` and filter by `notification.object as? AVPlayerItem === self.player.currentItem`, OR re-subscribe whenever the item changes.

### 11. CameraService — No `deinit`, notification handler closures + audio session not cleaned
`notificationHandler.onInterrupted/onInterruptionEnded/onRuntimeError` are set in `setupNotificationHandler()` but never cleared. `CameraNotificationHandler` does remove itself from NotificationCenter in its own deinit (✓), so notifications won't fire. But there's also no deinit-time `deactivateAudioSession()` — if CameraService is deallocated while audio session is active, the system audio routing is left in a custom category until something else changes it.
**Fix:** Add `deinit { deactivateAudioSession() }` and nil all notification handler closures.

### 12. RecordingViewModel.swift:117 — `countdownTask?.cancel()` doesn't stop in-progress camera setup
```swift
countdownTask?.cancel()                       // L117
state = .countdown(remaining: 5)
countdownTask = Task {
    if !cameraService.captureSession.isRunning { ... cameraService.setupSession(...) }
    ...
    for i in stride(from: 5, ...) {
        guard !Task.isCancelled else { return }    // ← only cancellation point
        ...
    }
}
```
**Why it misbehaves:** If user taps record, then quickly cancels and re-taps within ~300 ms, the previous task's `cameraService.setupSession()` is still on `sessionQueue` — not cancelable mid-flight — and may race with the new task's setup. The `isConfiguring` guard on `CameraService` mostly handles it, but the `setupSession` async dispatch isn't protected.
**Fix:** Add `Task.isCancelled` checks between camera setup steps, or serialize start-recording behind `await`.

## Tier 3 — Low priority / hardening

### 13. ComparisonViewModel.swift:188-200 — `swapVideos` doesn't pause first
Toggles `isSwapped` and restarts synchronizer without pausing players. Time observers can fire with stale references during the transition.
**Fix:** `pause(); isSwapped.toggle(); ...; resume(rate)`.

### 14. ComparisonViewModel.swift:161-171 — `seek(to:)` doesn't guard NaN
`clamp` propagates NaN. `seekPlayer` with `CMTime(seconds: NaN, ...)` is undefined; AVPlayer may freeze or play the wrong region. **Chain with #7:** missing contactTime → garbage syncOffset → seek arithmetic produces NaN → AVPlayer freezes.
**Fix:** `guard !time.isNaN, !swing1.startTime.isNaN, !swing1.endTime.isNaN else { return }`.

### 15. CameraService.swift:200 — `setCamera` reads `currentCameraPosition` off-queue
Read on caller's thread (likely main); written on `sessionQueue` at L134. Worst case: redundant `setupSession` call, mostly absorbed by the `isConfiguring` guard. Low impact, easy fix.
**Fix:** Read inside `sessionQueue.async`.

### 16. VideoExportService.swift:75-76 — `AVAsset(url:)` is deprecated
Should use `AVURLAsset(url: ..., options: [AVURLAssetPreferPreciseDurationAndTimingKey: true])`. PhotosSaveService L29 already uses the correct API.
**Fix:** Replace with `AVURLAsset` consistent with PhotosSaveService.

## Notes on findings NOT included

The agents flagged several items I rejected after verification:
- **Onboarding paywall close-button bypass** — by design (feature gates handle premium). UX/conversion concern, not a defect.
- **Force unwraps on static URL strings in AppPaywallView** — safe; the strings are constants. Style only.
- **`RecordingViewModel:159` callback assignment ordering** — already correctly nilled in deinit, error path, and cleanup (per past fix `7e7e72f`). The observed window between `cameraService.startRecording()` and `onFrameCaptured = ...` is microseconds; frames in that window would be silently dropped, which is correct behavior.
- **`DetectionOrchestrator.stop()` deadlock claim** — `processingQueue.sync` from main is intentional (FigSharedMemPool drain fix). Not a deadlock.
